# Enforce Archive-First Protocol for Spec Deletion

## Goal
Prevent data loss and orphaned remote issues by ensuring that any deletion of a local spec is gated by a mandatory remote archive operation. The engine must guarantee the remote state is archived before the local file is removed.

## Design Requirements
- **Guardrail Implementation:** The `ff archive` command (or any deletion logic) must be modified to implement an atomic "Archive-then-Delete" workflow.
- **Verification Step:**
  - Before local deletion, the engine must perform a remote API check to verify the issue has been successfully marked as `closed` or moved to the appropriate archive state on the `repo`.
  - If the remote confirmation fails, the engine must abort the local deletion and alert the user.
- **Atomic Operation:** The operation must be treated as a transaction—if the remote update fails, the local spec remains untouched.
- **Reporting:** Post-operation, the CLI must confirm: "Remote issue X archived; local spec Y removed."

## Implementation
- Added `DeleteSpecWithArchive` method to `LedgerEngine` that:
  1. Verifies remote issue is `closed` via coordinator before local deletion
  2. Aborts with error if remote issue is open or not found
  3. Only deletes local spec and ledger entry after successful remote verification
- Added comprehensive tests:
  - `TestDeleteSpec_ArchiveFirst_RemoteClosed_Succeeds` - remote closed → deletion succeeds
  - `TestDeleteSpec_ArchiveFirst_RemoteOpen_Aborts` - remote open → deletion aborted, local preserved
  - `TestDeleteSpec_ArchiveFirst_RemoteNotFound_Aborts` - remote 404 → deletion aborted, local preserved

## Acceptance Criteria
- [x] `ff archive` logic prevents deletion if the remote backend does not report success.
- [x] The CLI provides explicit feedback on the status of the remote archive before proceeding with file removal.
- [x] Any failure in the remote handshake results in zero changes to the local `specs/` directory.
- [x] Tests created to simulate a network failure during `archive` to ensure local specs are not deleted during an outage.

## Problem Statement

When `ff` is installed globally and run from a project directory, it cannot find the local `./ff` binary to copy to `.ff/bin/ff`, breaking the self-healing flow.

## Technical Requirements
- **Global Installation**: Provide a way to install `ff` globally (e.g., `ff --install` or `ff install`) that places the binary in a standard location on PATH (`/usr/local/bin/ff`, `~/.local/bin/ff`, or user-configurable).

- **Local Binary Reference**: The global `ff` must locate and use the project's local `./ff` binary (built from source) for self-healing into `.ff/bin/ff`. If the local binary doesn't exist, guide the user to build it (`go build -o ff .`).
- **Fallback Chain**: 
  1. If running as `./ff` (local), use current binary for self-healing (existing behavior)
  2. If running as global `ff`, find project root, then look for `./ff` in project root
  3. If no local binary, error with clear instruction to build it
- **Cross-Platform**: Support macOS, Linux, Windows (detect OS for binary name `ff` vs `ff.exe` and install paths)
- **Silent Auto-Init**: Maintain SPEC-1781295606 behavior — config and binary restoration happen automatically on first command

## Acceptance Criteria

- Running global `ff` from any subdirectory of a ForgeFix project initializes config and restores binary to `.ff/bin/ff`
- Running `./ff` from project root continues to work (backward compatible)
- If project has no local `./ff` binary, clear error: "Local ff binary not found. Run 'go build -o ff .' in project root."

## Impact
- Remote issue tracker becomes cluttered with "Resolved" issues that remain marked as "Open."
- Manual intervention required to close issues, defeating the purpose of the `ff sync` automation.
