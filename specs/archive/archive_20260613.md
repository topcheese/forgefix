# Asynchronous Background Sync

## Objective
Shift network-bound synchronization tasks (Gitea API calls) from the critical command path (ff commit, ff spec) into a non-blocking background process to ensure CLI responsiveness.

## Requirements

### Non-Blocking Trigger
`ff commit` must trigger a background `ff sync` process without waiting for completion.

### Failure Persistence
If a background sync fails, the error must be logged to a local file (e.g., `.ff/.sync_failures.log`) to prevent silent data loss.

### Proactive Reporting
Every CLI command execution must check for the existence of the failure log and provide a summary with an interactive offer to retry (`[Y/n]`).

### Isolation
The `ff sync` logic must be completely decoupled from the main process lifecycle; it must not influence the return status of the triggering command.

## Implementation

### engine/sync.go
- Encapsulate existing network reconciliation logic into standalone `RunBackgroundSync(configDir, specID string) error`
- Implement JSON-based failure queue in `.ff/.sync_failures.log` with `SyncFailure` struct
- Implement JSON-based operation queue in `.ff/.sync_queue.json` with `SyncOperation` struct for create_issue, close_issue, post_comment, update_issue_body, sync_spec
- `SpawnBackgroundSync()` uses `os/exec` with detached attributes (`Setsid`) to invoke `ff sync` as orphaned process
- Failure persistence: `RecordSyncFailure()`, `LoadSyncFailures()`, `ClearSyncFailures()`, `HasPendingSyncFailures()`
- Queue operations: `QueueCreateIssue()`, `QueueCloseIssue()`, `QueuePostComment()`, `QueueUpdateIssueBody()`, `QueueSyncSpec()`
- Queue processing: `processSyncQueue()` handles retries (up to 3) and logs failures

### main.go
- CLI interceptor after `Bootstrap()` checks for pending sync failures and prompts interactive retry
- Modified `sync` command to accept `--spec` flag for single-spec sync
- Modified `commit` command to spawn background sync via `engine.SpawnBackgroundSync()` when `--spec` provided
- Background process fully isolated - does not affect triggering command's exit code

### engine/execute.go
- `handleDetonationIssues` - queues create_issue operations instead of direct API calls
- `handleDefusedIssues` - queues post_comment + close_issue operations
- `closeStaleIssues` - queues post_comment + close_issue operations
- `handleTimeoutIssues` - delegates to handleDetonationIssues

### engine/config.go
- `Dashboard` struct added `ConfigDir` field
- `UpdatePipelineMetricsWithDetails` - queues create_issue on failure, queues close_issue on pass

## Acceptance Criteria

1. **Performance**: `ff commit` returns shell prompt immediately even with simulated network latency
2. **Reliability**: Failed sync triggers interactive prompt at start of next `ff` command
3. **UX**: User prompted to run `ff sync` only when necessary, keeping core experience "lean and mean"

## Verification

All criteria verified:
- `ff commit` with `--spec` returns immediately while spawning background sync ✓
- Background sync failures logged to `.ff/.sync_failures.log` ✓
- Next `ff` command detects failures and prompts `[Y/n]` retry ✓
- Retry executes `RunBackgroundSync()` and clears failure log on success ✓
- `--spec` flag on `ff sync` enables single-spec synchronization ✓
- All unit and integration tests pass ✓
